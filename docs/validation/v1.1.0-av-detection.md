# v1.1.0 audio/video source diagnostics

For each video/audio stream pair, the scanner calculates `audioStart - videoStart`, `audioDuration - videoDuration`, and `(audioStart + audioDuration) - (videoStart + videoDuration)`. Offset evolution is `endDelta - startDelta`. The duration ratio is `audioDuration / videoDuration` when both durations are valid and the video duration is positive. A null ratio means it cannot be calculated. A ratio is a timing clue, not a measured audio speed.

The start threshold is 0.250 seconds. Duration and end thresholds are the larger of 0.500 seconds and 0.05% of the longer stream. A value exactly on the threshold is accepted; only a larger absolute value produces a warning. These thresholds are intentionally less strict than remux validation because codec delay, edit lists, intentional silence and container rounding can be normal. A constant start offset is reported as an offset, not progressive drift. Drift is suspected when the offset changes beyond the duration threshold. Missing or invalid stream-local timeline data produces one informational `TimelineDataIncomplete` result for each affected video/audio pair and never falls back to the container duration.

The last scan retains the first 100 structured diagnostics for administrator display and retains aggregate counts for all scanned files. A single media file contributes once to the affected-media counter even if it has several issues. The UI displays a file name only; absolute paths are not stored in the last-scan snapshot.

The lightweight check (`EnableAudioVideoSyncCheck`, enabled by default) reads the stream descriptors already returned by the normal ffprobe invocation. A difference in duration alone does not prove an audible lip-sync defect. Optional packet analysis (`EnablePacketTimelineAnalysis`, disabled by default) samples the first and last two seconds using a separate ffprobe invocation when the lightweight check is enabled. It compares the first packet PTS and last packet PTS plus packet duration for each video/audio pair. Its `AudioVideoPacketDriftSuspected` warning uses the change in A/V offset between those samples. The packet probe has a timeout, cancellation, and a 20,000-packet cap. Short samples, B-frame presentation order, incomplete packets, or editing metadata can limit its conclusion; it is still a diagnostic rather than proof of audible desynchronization.

The scanner only reports source conditions. It does not correct timing, re-encode, retime, resample, remove streams, or make a file repairable because of an A/V diagnostic.

## Raspberry Pi 4 validation

On the real Jellyfin 10.11.11 ARM64 installation, the same read-only library of 129 files was scanned with `DryRun=true`. The v1.0.1 baseline took 17.17 s (CPU average/peak 166.48%/195.34%, RSS average/peak 308405/313088 KiB). v1.1.0 stream-descriptor analysis took 17.24 s (167.25%/195.34%, 295639/297764 KiB). Optional packet analysis took 30.95 s (124.73%/167.64%, 307381/308408 KiB). These are single-run samples, not statistically stable performance estimates. The default scan added no extra ffprobe invocation per media; optional packet mode does. The packet-mode cost supports its disabled default.

The v1.1.0 descriptor scan found 20 affected files and 74 diagnostics (24 duration differences, 24 end differences, 24 suspected drifts, and 2 incomplete timelines); packet mode added 7 packet drift warnings. The repair queue remained empty in both scans. Without a playback ground truth for each library file, these counts cannot establish a real-library false-positive rate. Controlled healthy A/V fixtures yielded 0 warnings across ten cases: MP4/AAC, MKV/Opus, MKV/AC3, MKV/EAC3, two-audio MP4, four frame-rate cases (23.976, 24, 25, 29.97 fps), silent final second, and VFR. The audio-only M4A produced no A/V issue. A deliberately one-second-short audio track produced duration, end, and drift warnings. VFR was verified by distinct nominal and average frame rates. All fixtures were generated in temporary cache storage and removed afterward.

The original regression backup had video/audio durations of 1427.000/1427.000 s and no source A/V warning, while reporting the known sample-count container defect. A stream-copy remux of a temporary copy had 1428.428867/1427.000 s, duration ratio 0.998999693, and duration/end/drift warnings. A temporary fixture manually corrected with `atempo=0.9989997` had 1428.428867/1428.392 s, ratio 0.999974191, and no A/V warning. Five other read-only backups in the same episode set had ratios from 0.999999986 to 1.000000008 and no A/V warnings. The original backup SHA-256 was identical before and after these probes.

The AAC/MP4 fixture exposed 1024 initial skip samples (AAC priming) and an MP4 `elst` edit-list atom. Neither caused a spurious start-offset warning. An intentionally unreadable MP4 and a truncated MP4 were classified `Unreadable` for their structural errors, with no A/V issue added. A temporary MP4 with a damaged H.264 packet was classified `Corrupted` (`INVALID_NAL_UNIT`); no source A/V warning upgraded or obscured that structural status. The packet probe timeout and cancellation both succeeded against a blocking FIFO on the Pi.

The exact final 1.1.0 ZIP was installed after successful upgrades from package versions 1.0.0 and 1.0.1; each upgrade loaded plugin version 1.1.0.0 with `DryRun=true` and a DLL matching the package. Three more read-only 129-file scans of that exact binary completed: A/V enabled took 17.48 s with 20 affected files, A/V disabled took 14.35 s with zero A/V diagnostics, and A/V plus packet sampling took 31.79 s with 7 additional packet drift warnings. All three left the repair queue empty and restored configuration, queue, and last-scan data. During these scans, a short authenticated HTTP media read completed in 49–73 ms and the Jellyfin information API averaged 44–51 ms; this checks basic playback responsiveness, not subjective lip-sync quality.
