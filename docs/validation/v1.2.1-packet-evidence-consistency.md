# v1.2.1 packet evidence consistency

## Problem

`PacketTimelineAnalyzer` samples two small windows (the first ~2 s and a
window requested at `duration - 2`). ffprobe anchors the end of a `%+2`
interval two seconds after the first packet read *after the seek*, and that
seek lands on an earlier keyframe. When one stream ends before the container
duration, or keyframes are sparse, the other stream's real end is not inside
the window, so `AvPacketEvidence.EndOffsetSeconds` (and `Drift`) can be far
smaller than the real stream-level difference.

Reproduced with a generic synthetic Matroska file (30 s video, 40.8 s audio,
keyframe every 5 s): stream metadata delta is +10.8 s, the sampled packet
drift is about +1.5 s. With `MaxAutoRepairDurationDeltaSeconds=2.0`, v1.2.0
classified this `AudioEndsLate` and planned an `AudioTrim` of the sampled
value; post-repair validation rejected the candidate and nothing was changed.

## Rule

`AvEvidenceConsistency.Reconcile` is the only place the rule lives. It is
called by `AvRepairClassifier` and, as a second guard, by `AvRepairPlanner`.

| Compared | Tolerance | Rationale |
| --- | --- | --- |
| start offset: metadata vs packets | 0.25 s (`OffsetSignalFloorSeconds`) | both are the first timestamps of the same streams |
| end offset: metadata vs packets | 0.5 s (`DriftSignalFloorSeconds`) | smallest drift treated as meaningful; the window legitimately misses the last packets (about 0.2 s measured) |
| drift: metadata duration delta vs packet drift | 0.5 s | same |

- Any difference beyond tolerance (including opposite directions) ->
  `Ambiguous`, confidence 0.3, `ManualOnly`.
- Packet drift at or above the floor while the metadata delta is below it ->
  `Ambiguous` (not corroborated).
- Metadata delta at or above the floor while the packets show none ->
  never `ConstantOffset`.
- Agreement within tolerance but on both sides of
  `MaxAutoRepairDurationDeltaSeconds` -> `Ambiguous`.
- Limits are checked against the larger of the two magnitudes; the amount to
  pad/trim is the metadata delta (what post-repair validation re-measures).
  The smaller value is never chosen.
- Stream `duration` is a length for some muxers and an end timestamp for others
  (e.g. an ffmpeg Matroska `DURATION` tag on a stream with a start offset).
  A second reading is only considered when the start offset is meaningful
  (>= 0.25 s). A file that starts in sync (the bounded pad/trim case) has one
  reading.

## Known limits

- The true stream end cannot be recovered from a partial window without
  reading the whole file, so it is not estimated.
- With a meaningful start offset, a file whose muxer reports a length can have
  an end mismatch that a partial packet window hides only if the other reading
  also happens to agree. Post-repair validation re-measures stream metadata and
  rejects such a candidate.
- A packet-confirmed, metadata-consistent end mismatch larger than
  `MaxAutoRepairDurationDeltaSeconds` is still `ProgressiveDrift` (two samples
  cannot tell an end-only change from a uniform drift); it is planned only with
  `AllowAudioReencode` and within `MaxAutoRepairDriftRatio`, as in v1.2.0.

## Validation

- Unit tests: `AvRepairClassifierTests`, `AvRepairPlannerTests` (cases A-F,
  tolerance boundaries, muxer duration semantics).
- Synthetic end-to-end (`tests/PiValidation`, `--av-repair-e2e`): case
  `partialTailWindowMustNotAutoRepair` (must be `ManualOnly`, no trim) and
  control `consistentBoundedTrimStillEligible`. Planning only, no repair is
  executed for these two cases.
