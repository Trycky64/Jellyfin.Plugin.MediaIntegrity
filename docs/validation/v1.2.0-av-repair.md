# v1.2.0 A/V repair

## Classification model

`AvRepairClassifier` compares each temporal-video/audio stream pair using two
independent signal sources:

- **Container/stream metadata**: `start_time` and `duration` per stream
  (always available).
- **Packet-level evidence** (`AvPacketEvidence`, from `PacketTimelineAnalyzer`,
  optional, enabled by `EnablePacketTimelineAnalysis`): the audio/video offset
  independently measured at the first and last sampled packet window, plus a
  bounded discontinuity check (a >0.75s gap between consecutive packets within
  one sampled window).

Classification never trusts metadata alone for anything actionable: without
packet confirmation, a stable-looking offset is `TimelineMetadataOnly`, and a
duration mismatch too large to be a single bounded pad/trim is
`DurationMismatch` — both always `ManualOnly` at the planning stage.

With only two sample points (start window, end window) it is mathematically
impossible to distinguish a *uniform* drift across the whole file from a
*bounded* change concentrated at one edge. This is resolved by magnitude and
by whether the file starts in sync:

- Offset stable, evolution negligible -> `ConstantOffset`.
- File starts in sync (`|offset| < 0.25s`) and the evolution is within
  `MaxAutoRepairDurationDeltaSeconds` -> `AudioEndsEarly`/`AudioEndsLate`
  (bounded, single-sided; safe for pad/trim).
- Otherwise -> `ProgressiveDrift` (only correctable, if at all, with an
  opt-in proportional audio time-stretch).

A hard, non-configurable 30-second ceiling (`AvRepairClassifier.GrossMismatchThresholdSeconds`)
overrides every other rule: any signal beyond it is always `UnsafeToAutoRepair`.
This directly encodes the project's real, previously-observed large mismatch
(a real-world A/V duration difference on the order of several minutes on one
title): diagnosed, never auto-repaired, regardless of how "clean" the pattern
looks.

## Planning and policy gates

`AvRepairPlanner` is a pure function of `(AvRepairDiagnosis, PluginConfiguration)`.
Every classification other than `ConstantOffset`/`ProgressiveDrift`/`AudioEndsEarly`/`AudioEndsLate`
is unconditionally `ManualOnly`. For the four repairable classifications, the
planner additionally requires, in order:

1. `EnableAudioVideoRepair=true`.
2. Confidence >= `MinRepairConfidence`.
3. Magnitude within the relevant configured limit (`MaxAutoRepairOffsetSeconds`,
   `MaxAutoRepairDurationDeltaSeconds`, or `MaxAutoRepairDriftRatio`).
4. For every strategy except `TimestampShift`: `AllowAudioReencode=true`.
   `AudioPad`/`AudioTrim` also gate on this even though the edit is
   conceptually lossless, because FFmpeg's `apad`/`atrim` filters require
   decoding and re-encoding the one targeted audio track.

`PlanMedia` additionally rejects (to `ManualOnly`) any audio stream that ends
up with more than one plan or with conflicting strategies — for example a
stream paired with two different eligible video streams. This never guesses a
combined repair.

## Execution

`AvRepairExecutionService` builds one FFmpeg invocation per plan. Every stream
is mapped explicitly, one `-map` per original stream index, in original
order — never a blanket `-map 0` with a corrective remap — so the output
stream order and count always match the source exactly, which is what
`StreamTimelineValidator`/`MediaValidationService` already require.

- `TimestampShift`: the source file is opened twice; the *first* input feeds
  every stream except the one target audio stream, and a second input with
  `-itsoffset <seconds>` feeds only that stream. Everything is `-c copy`.
- `AudioTimeStretch`/`AudioPad`/`AudioTrim`: single input; every stream is
  `-c copy` except the target audio stream, which gets `-c:a:<ordinal>
  <AudioReencodeCodec>` and `-filter:a:<ordinal> atempo=.../apad=.../atrim=...`,
  preserving the source sample rate and channel count.

A file needing repairs on more than one audio track chains stages
sequentially: each stage's validated candidate becomes the next stage's input.
Because every stage preserves the full, contiguous stream index range, a plan
targeting stream N is always still valid against the previous stage's output.

## Validation, replacement and rollback

The final chained candidate is validated with the *existing* v1.0.1/v1.1.x
`MediaValidationService` (stream identity, per-stream timeline tolerance,
chapters, full packet-copy pass) — completely unchanged for A/V repair. On top
of that, the candidate is re-probed and re-classified with
`AvRepairClassifier`; if any originally-targeted video/audio pair still
classifies as anything other than `None`, the repair is rejected before any
replacement is attempted.

Replacement reuses the existing transactional `MediaReplacementService`
unchanged: backup with SHA-256 verification and a recovery manifest, staged
copy, atomic swap, post-replacement validation, and automatic rollback to the
verified backup on any failure at any stage. `AvRepairTask` adds nothing new
here — this is the same code path `MediaRemuxRepairTask` already uses.

## Backup lifecycle

`DeleteBackupAfterSuccessfulValidation` (default `false`) only deletes the
per-file backup and its `.metadata.json` manifest immediately after
`MediaReplacementService.ReplaceAsync` reports `Success=true` and
`ReplacementCompleted=true` (which itself only happens after post-replacement
validation passed). A failed repair, a rejected candidate, or a rollback never
reaches that code path, so the backup is never deleted in those cases.

## Safety defaults

`EnableAudioVideoRepair=false`, `AllowAudioReencode=false`,
`DeleteBackupAfterSuccessfulValidation=false`. With defaults, classification
and stats are fully computed and visible every scan, but no A/V repair ever
runs and no A/V item is added to the automatic batch limit.

## Multi-track automatic repair is deferred

`AvRepairPlanner.PlanMedia` classifies and plans every audio track on a file
independently, but when **more than one** track on the same file is
auto-repair eligible, every one of those plans is downgraded to `ManualOnly`
rather than executed. This was discovered, not assumed: end-to-end testing
with real FFmpeg fixtures (below) found that chaining a stream-copy
`TimestampShift` pass with a following per-stream re-encode pass
(`AudioPad`/`AudioTrim`/`AudioTimeStretch`) on the *same* file can introduce a
small collateral timestamp shift (tens of milliseconds) on completely
untouched streams, including video, that this release cannot yet prove safe.
Single-track repairs (`TimestampShift` alone, or one re-encode strategy
alone) do **not** exhibit this and are fully repaired automatically. Each
track's classification and would-be plan remain fully visible for manual
review even when downgraded.

## Real, credential-free end-to-end validation

Raspberry Pi validation for this release could not use Jellyfin's HTTP API
(`JELLYFIN_API_KEY` is not configured on this host, and one was deliberately
not created — see the release report). Instead, `tests/PiValidation` gained
an `--av-repair-e2e` mode that exercises the exact production classes
(`MediaProbeService`, `PacketTimelineAnalyzer`, `AvRepairClassifier`,
`AvRepairPlanner`, `AvRepairExecutionService`, `MediaValidationService`,
`MediaReplacementService`) against real FFmpeg-generated fixtures in a
throwaway sandbox — never touching the real media library.

Run on the Raspberry Pi 4 target host (ARM64, Debian 12, ffmpeg 5.1.9) with
`dotnet tests/PiValidation/bin/Release/net9.0/PiValidation.dll --av-repair-e2e`:

- **ConstantOffset -> TimestampShift**: a real MKV fixture with a genuine
  1.5s `-itsoffset` audio delay was classified `ConstantOffset` (confidence
  0.92, packet-confirmed), planned as `TimestampShift`, repaired with a real
  FFmpeg stream-copy pass, passed full candidate validation, re-classified as
  `None` (the offset was actually gone, not just "ffmpeg exited 0"), and
  successfully replaced through the real transactional backup/replace
  pipeline with a SHA-256-verified backup.
- **AudioEndsEarly -> AudioPad**: a real MP4 fixture with a genuine 1s
  audio deficit was classified, planned as `AudioPad`, repaired with a real
  `apad` re-encode of only the audio track, validated, re-classified `None`,
  and replaced successfully.
- **Backup lifecycle**: with `DeleteBackupAfterSuccessfulValidation=true`, the
  backup and its `.metadata.json` manifest were confirmed present immediately
  after a successful repair and confirmed deleted only afterward.
- **Multi-track**: a fixture with two independently anomalous audio tracks
  was correctly classified as `ConstantOffset` and `AudioEndsEarly`
  respectively; per the scope decision above, both plans were downgraded to
  `ManualOnly` and neither was executed.

This testing also uncovered and fixed a real defect: `StreamTimelineValidator`
(shared, unmodified logic from v1.0.1/v1.1.x) rejected every legitimate
`TimestampShift`/`AudioPad`/`AudioTrim` candidate, because it was written for
pure remux, where any `start_time`/duration change is a red flag — but an A/V
repair's entire purpose is to deliberately change exactly that, for exactly
one targeted stream. `MediaValidationService.ValidateAsync` and
`MediaReplacementService.ReplaceAsync` now accept an optional
`intentionallyRetimedStreamIndexes` set (populated by `AvRepairTask` from the
plan's own `AudioStreamIndex`) that excludes only those specific streams from
the duration/start-time/drift checks, while every other stream — including
video — remains fully, strictly validated against the source, both before and
after replacement.

Fixture generation also required dense keyframes (`-g 5 -keyint_min 5`):
FFmpeg's `-read_intervals`-based tail-window packet sampling (used by
`PacketTimelineAnalyzer`) needs a nearby keyframe to seek accurately, which a
short synthetic clip with one giant GOP does not provide. This is purely a
fixture-realism concern; real-world media is virtually never encoded with a
single multi-minute GOP.

## Real-library classification dry run (read-only, credential-free)

The `Media Integrity Scan` scheduled task could not be triggered without
`JELLYFIN_API_KEY` (see below), so `tests/PiValidation` gained a
`--real-library-scan <root>...` mode that runs the exact production
`MediaProbeService`/`PacketTimelineAnalyzer`/`AvRepairClassifier`/`AvRepairPlanner`
code directly against files enumerated from the filesystem — never through
Jellyfin's library index, never writing anything. Run against the real,
already-configured library roots on 2026-09-18:

```
filesFound: 130, checked: 130, healthy: 105, warning: 25, unreadable: 0
avAffectedMedia: 29
classificationCounts: Ambiguous=22, UnsafeToAutoRepair=4, AudioEndsEarly=7, AudioEndsLate=1
wouldPlanCounts (repair hypothetically enabled): ManualOnly=31, AudioPad=2, AudioTrim=1
writesPerformed: 0
```

This closely matches the previously documented v1.1.1 baseline (104 healthy,
25 warnings, 0 unreadable, 18-affected-media on the lighter metadata-only
pass; more pairs cross the classification floor here because packet evidence
was fetched for every file, matching the deeper "63 diagnostics" packet pass
already documented for this library). No `ConstantOffset` (`TimestampShift`)
candidates exist in the real library; the four `UnsafeToAutoRepair` cases
include the previously documented large real-world mismatch, correctly kept
out of any automatic path regardless of configuration. With this release's
actual defaults (`EnableAudioVideoRepair=false`), **zero** of these 130 real
files would be queued for automatic A/V repair; even with repair
hypothetically enabled, only 3 files (2 `AudioPad`, 1 `AudioTrim`) would ever
become eligible, all bounded, single-sided, packet-confirmed corrections.

## Not yet validated

The live Jellyfin-task-orchestrated path (scanning the real 129-file library
through the **Media Integrity Scan** scheduled task, and a real single-file
pilot repair through the **A/V Repair** scheduled task) requires the
Jellyfin HTTP API to trigger and inspect. No `JELLYFIN_API_KEY` exists on
this host, and per explicit operating instructions one was not created. See
the v1.2.0 release report for how this affects the release decision.
